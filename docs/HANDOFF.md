## Goal

FreeKiosk is an open-source Android kiosk app (React Native + TypeScript + Kotlin native modules). This work supports one specific production fleet: Kyocera DuraForce2 devices (Android 10), enrolled in Headwind MDM (HMDM) as Device Owner, running FreeKiosk pinned to a warehouse/logistics web app (referenced as `operations.octane.store` — a real site, not a placeholder) for barcode scanning on camera- and image-heavy pages. The user operates this fleet and reports real field symptoms; the job is diagnosing and fixing them without guessing, verifying every hypothesis against actual source or actual device logs/field tests before shipping anything.

**Working style established in this thread, worth preserving**: this branch has a long, consistent track record of hypotheses that looked right and turned out wrong on contact with real evidence (see "Key decisions" below). Default to verifying against source/logs/field tests before proposing a fix, not after — and verify against the actual git history, not a memory of it (that's the mistake this very file was corrected for).

### Shipped and working — the two most important individual fixes

- **`MotionDetector` must mount unconditionally — this is deliberate, not an oversight, do not re-gate it.** `camera-teardown` (v1.2.33) originally gated mounting `<MotionDetector>` on the motion-detection feature being enabled, on the theory that vision-camera's `CameraDevicesManager` init (camera enumeration + availability callback) was a same-process hook *interfering* with the WebView's `getUserMedia`. **Field testing showed the exact opposite**: with motion detection off (this fleet's actual default), the WebView's barcode-scanner camera opened but decoded slowly and unreliably (5-6s of repositioning, sometimes never) against instant on Chrome on the same device. Toggling motion detection on — nothing else about the build changed — fixed it immediately, confirmed both directions on the affected device. Reverted in v1.2.42 (commit `a634823`): `MotionDetector` is now mounted unconditionally in `KioskScreen.tsx` (confirmed at current `HEAD`: `<MotionDetector enabled={isFocused && (motionAlwaysOn || (motionEnabled && ...))} ... />` — always rendered, only the `enabled` prop gates actual capture). **If you see this unconditional mount and think "we should only mount this when motion detection is used, that's wasteful" — don't. That exact change was tried, and it broke barcode-scan reliability fleet-wide.** The other two fixes from the same original v1.2.33 commit (the `CameraPhotoModule` leak guards, the `getUserMedia` diagnostic logging) are unrelated and were kept.
- **WebView console logging now actually reaches logcat — the chain is two levels deep, understand it before you assume something "isn't in the fleet build."** `RNCWebChromeClient.onConsoleMessage()` discards every page console message in release builds by default (`return true`, no forwarding) — and FreeKiosk ships release-only. This silently no-op'd every `[FreeKioskCam]`/`[FreeKioskNet]` diagnostic log from day one; an `onConsoleMessage` *prop* was tried first (v1.2.?? era) and does nothing because it isn't a real prop in `react-native-webview` 13.16.0 at all. The real fix (commit `47a5c30`, shipped in the v1.2.42 bundle) patches `RNCWebChromeClient` itself to forward to logcat under tag `FreeKioskWebConsole`. **This fix lives inside `freekiosk-webview-resilience-v1.2.19.patch` as a hunk that edits the *text* of `patches/react-native-webview+13.16.0.patch`** — which is itself a patch-package patch applied to `node_modules/react-native-webview` by the `postinstall` hook (`patch-package`) when `npm install` runs during the fleet build (see Architecture below for why this two-level mechanism is required and how to verify it). **Confirmed present at current `HEAD` in both files.** `adb logcat | grep FreeKioskCam` (or `FreeKioskNet`, or `FreeKioskWebConsole` for everything) works today, on the real fleet build. Do not conclude a diagnostic log "won't reach logcat" without checking both the root patch *and* whether it edits a nested `patches/*.patch` file — checking only `patches/react-native-webview+13.16.0.patch` on the branch and reasoning "branch files don't reach the fleet" is an easy, previously-made mistake; the root `freekiosk-webview-resilience` patch is what actually delivers that file's content to the build.
- **`return_tap_count` dual-mode fix**: ungated/immediate when pushed standalone (no `config_version` in the push), gated/bulk when part of a versioned config push (commit `33e6a63`, v1.2.43) — restores the field it was before an earlier, too-broad ungating change.
- **`MotionDetector` orphaned-timer leak fix** (commit `bb50487`, v1.2.44) — a *different* bug from the mount-revert above: `stopDetection()` only cleared the capture `setInterval`, never the pending 1.5s `CAMERA_READY_DELAY` `setTimeout`. A rapid enable/disable within that window left the timeout armed with a stale closure; it fires anyway and arms a capture interval nothing can ever clear (the ref gets silently overwritten next cycle). Only a full process kill (not a WebView remount) clears it, since this runs in Hermes/React Native, not the WebView's Chromium engine — matches a field report of camera trouble surviving a page reload/WebView remount but not a device restart. Fixed by tracking `startDelayTimeout` and clearing it in `stopDetection()`.
- **Duplicate "already matched device" WARNING fix + `config_version: "0"` bypass sentinel** (commit `c266b11`, v1.2.45, current `HEAD`): a real race — `apply()` in `useManagedConfigSync.ts` ran unserialized from two independent native triggers (system broadcast + `HeadwindMDM.EventHandler`, both intentional on the native side). When both fired within milliseconds, both calls read the last-applied version/fingerprint before either had written its own, both passed the version gate, and the second's per-field diff saw the first's just-written value and logged "already matched" too — a duplicate WARNING with one extra field. Fixed by chaining `apply()` through a shared promise so a queued call only starts once the previous one has fully persisted. Also added `config_version: "0"` as a repeatable "apply this push right now, don't persist as last-applied version" bypass (documented as convention 9 in `applyManagedConfig.ts`'s doc comment).
  - **Known follow-on, not a bug, not yet decided**: `"0"` has no redelivery dedup by design (that's the tradeoff for always-applying). HMDM re-sends the full restrictions bundle on every sync/app restart; if `config_version` stays `"0"`, you get a fresh full WARNING log every time nothing actually changed. Options on the table, undecided: downgrade that log line's severity, give `"0"` its own short-lived dedup memory, or treat `"0"` as a one-shot lever (push it, then push a real version number) rather than something to leave standing.
- **Upstream merge is a verified no-op for the fleet APK, for two independent reasons**: this fork was 4 commits behind `RushB-fr/freekiosk` (#208 native screen-lock fix, #209 `/api/mode` wiring, #211 stop random WebView refresh via broadened `android:configChanges`). Merged cleanly as `65a9687`, current `HEAD`. Confirmed a build no-op by replaying the full 10-patch stack from a fresh `v1.2.19` checkout before/after the merge and comparing resulting git tree hashes (identical). Reason 1 (general): branch `src/` never reaches the fleet build regardless (see Architecture). Reason 2 (specific to these commits): this branch already had its own independent implementation of all three — commit `e5cf008` (2026-07-17, weeks before the merge) is literally titled "Wire /api/mode runtime switch (#209) and stop random WebView refresh (#211)", and #208 was already present per an even older commit. **Neither this branch's own versions nor the newly-merged upstream versions of #208/#209/#211 have ever been backported into the root patch stack — see "Known gap" below, this is a real, currently-true hole, not just a historical note.**
- **3 real historical bisection checkpoint APKs** built and delivered (v1.2.31 wakelock-only, v1.2.33 camera-teardown, v1.2.40 resilience-loop) plus v1.2.27, to isolate a **device-to-device** barcode-scan-lag variance (see "Investigated and resolved" below — this is a different symptom from the MotionDetector-mount bug above, don't conflate them).

### Investigated and resolved (root cause understood, fix is operational, not code)

- **Device-to-device camera/scan-lag variance under HMDM** (a 6-device on/off test matrix). Narrowed to two devices with identical config, one snappy one laggy. Eliminated, in order, with evidence each time: location-tracking (fixed one device, not the other — two separate problems); GMS/Play Store version staleness (updated it, didn't fix the still-laggy device); native `BarcodeDetector` availability (confirmed present and byte-identical on both devices via live JS injection through FreeKiosk's own `/api/js` REST endpoint); WebView/FreeKiosk-*code*-specific causes (ruled out once Chrome was confirmed ALSO slow on the laggy device — same hardware, same WebView engine, so a FreeKiosk-code-specific explanation would have to also hit Chrome, and it was ruled out for *this specific device-pair symptom only* — it does **not** mean no FreeKiosk-code camera bug has ever existed; the MotionDetector-mount bug above is a real, separate, confirmed one. Don't conflate the two threads.).
  - **Actual root cause for this thread**: QR-code Device Owner provisioning skips Android's Setup Wizard, which normally triggers the one-time "update all preinstalled Google apps" sweep on a fresh device. MDM-provisioned devices never get this sweep, so GMS-adjacent components stay stale indefinitely (confirmed: a factory-reset, *unenrolled* device updates fine; the same device re-enrolled into MDM does not).
  - **Fix is process, not code**: let a freshly-reset device sit online unmanaged for 10-15 min (let Play Store visibly finish updating) *before* enrolling it into MDM. For the already-enrolled fleet: manually trigger Play Store "Update all" per device as a retrofit.
  - Also established: HMDM (this stack) has **no Managed Google Play / Android Management API integration** (checked `hmdm-server` source directly, zero matches) — no IT-enforced guarantee available, only the operational discipline above plus periodic manual verification.
  - HMDM's own code was reviewed in depth for this thread and is **not implicated**: it never touches the camera (zero references anywhere in `hmdm-android`), its Community Edition kiosk/overlay/accessibility features are all `ProUtils` stubs that don't run, and its background services (`StatusControlService` at a 10s fixed-cost loop, etc.) are content-blind and don't scale with what's on FreeKiosk's screen.

### Investigated, hypotheses eliminated, **root cause still unconfirmed** — the two live threads

**1. WebView freeze/scroll-lag on image- and scan-heavy pages (the primary open issue).**

Symptom: on pages with 50+ images and 50+ barcode scans (each scan involves camera open → decode → close, repeated), the page's menu bar and profile icon become unselectable, scrolling stays smooth, and images on the page go blank. A normal reload does not fix it; only the existing triple-press hard reset (now a true fresh-renderer `webViewKey` remount, not just `reload()` — see v1.2.42 above) does. Never reproduces in Chrome on the same device. **This is observed on top of the entire resilience arc above** — camera wrapper v3, the real hard-reset remount, `onRenderProcessGone` auto-recovery, debounced PDF observer are all already shipped and this still happens, which is informative: whatever is degrading these pages survives a fairly mature resilience layer already tuned for camera-HAL races specifically, pointing at a broader, cumulative resource issue rather than a single camera-open race.

Hypotheses raised and **disconfirmed with real evidence** (do not re-propose without new evidence):
- IME self-heal `OnGlobalLayoutListener`/watchdog loop in `freekiosk-keyboard-fix-v1.2.19.patch` (`MainActivity.kt`) — looked like a strong fit (always-on per-layout-pass Binder IPC, gated to API<30 which matches this hardware). **Disconfirmed**: a `FreeKioskIME`-tagged logcat capture across 9 real keyboard open/close cycles on-device showed padding cleanly converging `0 → N → 0` every single time, zero `watchdog corrected stale padding` lines. The padding never sticks on this hardware; this mechanism isn't firing.
- `onConsoleMessage`→logcat bridge flooding the UI thread with every page console message — considered, but **this bridge's existence/reach was itself initially misjudged (corrected above): it DOES reach the fleet build** (as of v1.2.42, see the dedicated entry above). Flooding-the-UI-thread-via-console-spam remains a theoretically re-testable idea if console volume on the real page turns out to be very high, but it was not confirmed as the cause and the earlier "it can't even reach the fleet so it's moot" reasoning was wrong — don't cite that specific reasoning again.
- Keyboard-mode `MutationObserver` doing unthrottled full-DOM `querySelectorAll` scans per mutation — real code, real risk in general, but **ruled out for this fleet**: Keyboard Mode = Default, so neither observer variant is injected.
- `shouldInterceptRequest` PDF proxy hook — checked, it's gated on a `file:///android_asset/pdfjs/` path check, so on this fleet's https page it costs one cheap string check per request, not a real factor. (Separately, the *other* PDF-link observer — the one that rescans anchors on DOM mutations — was already debounced to 2/sec in v1.2.34, see above; not a live factor either.)
- "autoReload periodically reloads the page, so nothing ever gets a fresh renderer" — **wrong, corrected mid-investigation**: `autoReload` is error-driven only (5xx response or load failure → one 5s-delayed retry), there is no periodic timer at all. Don't resurrect "turn off autoReload" as a test — it proves nothing on a healthy page.

**Leading hypothesis, NOT YET CONFIRMED — this is the single most important next step**: the WebView renderer process is memory-starved, not CPU-blocked. Reasoning: the exact symptom triad (unselectable UI + blank images + smooth scroll) matches a starved Chromium main thread specifically — scroll is compositor-driven and survives even when the main thread (hit-testing, JS dispatch, image decode) doesn't. Supporting, verified facts: there is **no `onTrimMemory`/`onLowMemory` handler anywhere in this codebase** (grepped both `android/` and `src/`, zero matches); no `android:largeHeap` (tried once, reverted — see commit `a65ea87` — as a blind "mask the symptom" attempt before this investigation, not evidence either way on its own); the `onRenderProcessGone` recovery from v1.2.32 is confirmed NOT firing during this freeze, meaning the renderer is degraded-but-alive, a state the app currently cannot detect or recover from except via the manual triple-press. The camera-cycling pattern (50+ open/close cycles per session) plus `CAMERA_RESILIENCE_JS`'s own proactive release/reopen cycling (`releaseStaleVideo()`, on top of whatever the page's own JS does) is a plausible **amplifier** of a known Chromium-Android video-capture memory-leak risk class under rapid cycling — not necessarily the sole cause.

**The decisive measurement, not yet taken**: `adb shell dumpsys meminfo <webview-renderer-pid>` captured *while the page is actually degraded* (blank images, dead menu bar), then again immediately after the triple-press recovery. A large PSS drop across that recovery would confirm the hypothesis; a flat reading would refute it and reopen the investigation. **Top priority next step.**

Separately, effort went into getting this measurement (or something close) **without a new fleet rebuild**, per the user's explicit, standing preference. Established:
- FreeKiosk's own `/api/memory` REST endpoint (`KioskHttpServer.kt`) ships as-is on the fleet but only reports system-wide `ActivityManager.getMemoryInfo()` — not renderer-specific.
- HMDM's `PushMessage.TYPE_RUN_COMMAND` (`hmdm-android`, `PushNotificationProcessor.runCommand()`) runs an arbitrary shell command via `Runtime.exec()`, result capped at 200 chars, reported through `RemoteLogger`. Full round trip traced end to end: server-side `PushApiResource` (`POST /rest/private/push`, needs `push_api` permission) sends; `hmdm-server`'s `DeviceLogResource.java` (under the "Device Log" plugin) both serves the per-device log rules and receives uploads, gated by the plugin being enabled. User confirmed their live server matches the locally cloned copy and that their config already satisfies both prerequisites (Device Log plugin enabled; a Verbose-level log rule exists for `com.hmdm.launcher`, which covers `runCommand`'s DEBUG-level messages).
- Working `curl` payload handed off: `POST https://<hmdm-server>/rest/private/push`, `messageType: "runCommand"`, `payload` a shell command, targeted via `deviceNumbers`. Recommended command: `cat /proc/meminfo | grep -E "^(MemTotal|MemFree|MemAvailable|Cached):"` — NOT `dumpsys`, which will almost certainly fail through this channel since `Runtime.exec()` from a plain app process (even Device Owner) lacks the `android.permission.DUMP` permission `dumpsys` requires.
- **Not yet tested by the user as of this writing.** This is coarse (system-wide, not renderer-specific) even if it works — it does not replace the `dumpsys meminfo <renderer-pid>` measurement above, which still needs physical `adb` access.

**2. `WIFI_BSSID_CHANGED` log entries show fabricated MAC addresses — root cause genuinely unknown.**

`com.hmdm.launcher`-tagged device log entries like `WIFI_BSSID_CHANGED 92:41:b2:82:56:0f ssid="LAAM Office"` where the BSSID doesn't match any real access point MAC, while the SSID and roaming-event timing are correct. Sampled BSSIDs have the locally-administered bit set in their first octet — the signature of a generated/randomized address, not a real factory-assigned radio MAC.

**Exhaustively searched and ruled out, with evidence**: the literal string `WIFI_BSSID_CHANGED` (or `BSSID` in any casing) does not exist anywhere in `hmdm-android`, `hmdm-server`, or `freekiosk` — checked via case-insensitive grep, ripgrep bypassing `.gitignore`, and `git log --all -p` on both shallow HMDM clones. FreeKiosk's own Wi-Fi code (`WifiControlModule.kt`/`WifiDialog.tsx`) is an unrelated, user-facing Wi-Fi picker — not a background roaming monitor — and its one use of the shared HMDM logging API correctly self-identifies as `com.freekiosk`, never `com.hmdm.launcher`.

**A genuine, separate security finding surfaced while investigating this** (independent of whether it's the actual BSSID mechanism): `PluginApiService` in `hmdm-android` (`app/src/main/java/com/hmdm/launcher/service/PluginApiService.java`) exposes an AIDL service any app on the device can bind to (`exported="true"`, no permission). Four methods — `log()`, `queryAppPreference()`, `setAppPreference()`, `commitAppPreferences()` — accept a caller-supplied `packageId` with **zero validation against the real calling app's identity**. Any app can forge log entries appearing to come from another package, or read/write another app's HMDM-managed preferences. Fix designed (replace the claimed `packageId` with one derived from `Binder.getCallingUid()` + `PackageManager.getPackagesForUid()`) but **not implemented** — needs `add_repo` re-invoked with push access to `hmdm-android`, plus explicit user go-ahead on scope.

Next steps for this thread (none completed): watch `adb logcat` filtered on "BSSID" live during an actual AP roam to catch the real emitting process's PID; or check whether Headwind MDM Pro is licensed on this deployment (the open-source `ProUtils` class is a confirmed no-op stub — if Pro is active there may be closed-source Wi-Fi/roaming code invisible to everything checked so far).

## Key decisions made and why

- **Patch-stack discipline, no exceptions**: every fix to anything the fleet APK actually ships goes into the relevant root-level `freekiosk-*.patch` file, verified by a full 10-patch replay from a fresh `v1.2.19` checkout before trusting it — never by editing `src/`/`patches/` and assuming it reaches the build. Every single commit in this branch's history (dozens, see `git log`) ends its message with this verification. The one known exception (#208/#209/#211, "Known gap" above) is exactly why this discipline matters — it's the one place it slipped, and the result is three real fixes with zero field effect for months.
- **`MotionDetector` mounts unconditionally, on purpose — do not re-gate it on `motionEnabled`.** See the dedicated entry above. This is the single most likely "obvious cleanup" a future pass could get wrong.
- **Verify before shipping, every time, including against git history itself**: this thread has a long record of plausible-sounding hypotheses that were wrong on contact with evidence — IME self-heal, the original "console bridge can't reach the fleet" claim, "autoReload is periodic", an early wrong claim that the `hmdm-server` log-rules endpoint didn't exist, and (most recently) an entire handoff draft written from a conversation summary that missed 15+ real shipped commits. Every one was caught by actually reading shipped source, device logs, or `git log` rather than trusting a plausible narrative or a memory of one.
- **"0" bypass sentinel traded away redelivery-dedup on purpose**: a deliberate design choice (the point was to skip the version-gate check), but its consequence (noisy re-logging under normal launcher redelivery) wasn't weighed at design time. Worth knowing before "fixing" it reflexively.
- **#208/#209/#211 were never backported into the patch stack** — true before the upstream merge, still true after it (see "Known gap" above). Not a decision made *during* the merge; a pre-existing gap the merge didn't address either way.

## Architecture / setup notes

**The single most important thing to understand about this repo**: there are two completely different "what actually ships" answers.

- `git diff`/`src/`/`android/` on this branch reflect ordinary React Native + Kotlin source, buildable the normal way (`npm run android`, or `cd android && ./gradlew assembleRelease`, output at `android/app/build/outputs/apk/release/app-release.apk`). Requirements: Node 20+, JDK 17+, Android SDK 26+.
- **The actual fleet APK is NOT built this way.** `.github/workflows/build-freekiosk-apk.yml` (manual `workflow_dispatch`, inputs `source_tag` default `v1.2.19` and a mostly-vestigial `patch_file` input) copies the 10 root-level `freekiosk-*.patch` files to `/tmp` *before* switching the tree to the tag, applies them in a fixed order (`battery-lock` plain `git apply`, then `refresh-button → managed-config → patch-flags → keyboard-fix → boot-launch → screen-sleep → webview-render-recovery → camera-teardown → webview-resilience`, all `--3way` with `git add -A` after every single apply — **do not reorder or skip the `git add -A` steps**), `sed`-stamps `versionCode 68`/`versionName "1.2.45"` into `android/app/build.gradle`, then runs `npm install --no-audit --no-fund` (Node 20) and `./gradlew assembleRelease` (JDK 17, Android SDK platform 36 / build-tools 36.0.0 / NDK 27.1.12297006 / cmake 3.22.1), signing with the fleet keystore if `KEYSTORE_BASE64`/`KEYSTORE_PASSWORD`/`KEY_ALIAS`/`KEY_PASSWORD` secrets are set (falls back to the debug key, with a warning, if not). **Editing `src/` or `patches/` on this branch alone has zero effect on the fleet APK.** Only the 10 `freekiosk-*.patch` files and the workflow itself reach it. Proven, not assumed, by replaying the stack before/after the recent upstream merge and comparing resulting git tree hashes (identical both times).
- **The patch system is actually two levels deep, and this matters for any fix touching a vendored library (`react-native-webview`, `vision-camera`, etc.), not just FreeKiosk's own code.** `npm install`'s `postinstall` hook runs `patch-package`, which applies every `patches/*.patch` file to the matching `node_modules/` package. Since `patches/react-native-webview+13.16.0.patch` (etc.) is itself a tracked file in the FreeKiosk repo, a root-level `freekiosk-*.patch` **can and does** include a hunk that edits the *text* of that nested patch file — which then gets applied to `node_modules/react-native-webview` by `patch-package` during the fleet build's `npm install` step, same as it would for a local dev build. The WebView-console-logging fix (above) works exactly this way: `freekiosk-webview-resilience-v1.2.19.patch` edits `patches/react-native-webview+13.16.0.patch`'s content, which `patch-package` then applies to the real RNW library source. **When checking whether a vendored-library-level fix reaches the fleet, check both: does any root `freekiosk-*.patch` touch `patches/<library>.patch`'s text, AND does the resulting `patches/<library>.patch` content actually get applied (it will, via `postinstall`, as long as the file ends up with the right content before `npm install` runs — which it will, since root patches apply before `npm install` in the workflow).**
- **Regenerating a patch that touches a file another patch *also* added or that is itself a nested patch file** (common — several patches touch `WebViewComponent.tsx`/`KioskScreen.tsx`/`MainActivity.kt`, or `patches/react-native-webview+13.16.0.patch` as above) can't be done by diffing against an already-patched tree, since `git apply` needs to see the file being *created*, not modified, if it doesn't exist before that patch runs. Method: build a clean "before" worktree (tag + every patch *up to but not including* the one being changed), build an "after" worktree with your edits applied on top, then `git diff --no-index --no-prefix` the two and fix up the path prefixes/headers (`fk-before/`→`a/`, `fk-scratch/`→`b/`, and the newly-added-file header artifact `diff --git b/X b/X` → `diff --git a/X b/X`). Always finish with a full 10-patch replay from a fresh tag checkout, hard-failing on any non-clean apply, before trusting the result.
